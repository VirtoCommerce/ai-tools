The defect

The storefront Experience API publishes contact.firstName, .lastName and .fullName as non-null GraphQL fields over nullable Contact columns. A rep saved without a name therefore fails every query that reads the current user — including the sign-in page context — so the account is locked out of the storefront entirely.

The fix makes both names required: SalesRepDetailsValidator runs before anything is persisted on the /api/sales-rep aggregate save path, and the VC-Shell details blade gates Save behind the same rule. fullName is derived from the parts, so requiring them covers all three fields.

Notes — none blocking

  • The root cause is untouched and still reachable. On the fixed build, PUT /api/members still clears a rep’s names at 204, and the storefront then fails with INVALID_OPERATION again. The validator guards only the /api/sales-rep path; the Contacts blade, /api/members, customer import and the storefront’s updatePersonalData remain uncovered. Scoped out deliberately by the PR — but the bug class is not closed, only this entry point.
  • fullName goes stale. Same probe: /api/members does not recompute it, so a contact can hold fullName: "Green Verified" with both parts null. Pre-existing, unrelated to this PR.
  • Existing nameless reps are not repaired — as documented. Not exercisable here: all 22 reps on vcptcore-qa have both names.
  • Cosmetic (P3). The blade prints the raw model key — “The firstName field is required” — beside a label reading “First name”.
  • Environment, not product. On vcptcore-qa the classic AngularJS manager forces admin to #!/changepassword. VC-Shell is not gated by it, so verification was unaffected; the password needs rotating before any classic-blade work on this stand.

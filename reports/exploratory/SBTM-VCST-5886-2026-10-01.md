## STOP — Critical finding (lane halted per charter)
**PO-3X-C1 — punchout:create → Administrator privilege escalation via the mapping userId.**
`POST /api/punchout-user-mappings` takes a caller-supplied `userId` and does NOT validate it against the
mapping's `memberId`/contact, nor reject administrator accounts. Mapped the ADMIN account
(`1eb2fa8a`, isAdministrator) to an external identity, then ran a normal anonymous cXML
PunchOutSetupRequest (config 0 secret) → setup Status 200 → `grant_type=punchout` redeem →
**HTTP 200 access_token with `role=__administrator`, `channelId=punchout`**; `/api/platform/security/currentuser`
returns `admin / isAdministrator:true`. The grant handler (PunchoutGrantTypeHandler.ValidateGrantAsync)
only checks user-exists / not-locked-out / CanSignInAsync — an admin passes all three. So a back-office
user holding only `punchout:create` can escalate to full administrator; the sign-in half of the chain is
anonymous (cXML POST + shared secret). Confirms model row #30 / PROPOSED-BL-PUNCHOUT-002.
Severity guess: Critical. Evidence: scratchpad/po3x/a2.mjs output (23:5x–00:0x UTC).

Corroborating (same run): CROSS mapping (USER2 account onto USER's contact memberId) redeemed as USER2
(`sub=488ab8fd`) — the signed-in principal is the mapping's `userId`; `memberId` does not constrain it.
ADMIN2 mapping (admin userId, no memberId) also redeemed as admin. So `userId` is the sole identity source.

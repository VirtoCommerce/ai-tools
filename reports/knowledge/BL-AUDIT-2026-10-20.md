# BL audit: 2026-10-20 (auth: org fallback after VCST-6132)

Scope: BL-AUTH-012, BL-AUTH-013, BL-AUTH-016. Mode: `/qa-review-bl` (`bl` axis), human-source sync. Trigger: the `/qa-test` VCST-6132 run.
The `tc:scope` / 1c / 3x / 4a / C1 runs all observed that BL-AUTH-013/016 still described the fallback as "password grant only".

## Human source
- **VCST-6132**: description (the cases table and Expected).
- **Dmitry Grishin, QA comment 2026-10-14:**
  - The fallback applies to every credential sign-in, i.e. every token request that sets `SignInResult`: `password`, `otp_email`, and `mfa` once it ships.
  - An explicit switch (`refresh_token`) still fails.
  - Locked in both orgs → sign-in succeeds with no organization.
  - Rejected / Invited / Deleted in both → the membership-status error, the same as for password.
- **Dmitry Grishin, reply 2026-10-20 (comment 112185):** the fallback order and the sign-in log are outside VCST-6132 and are tracked as VCST-6352 and VCST-6438.

The change is vc-module-customer PR #321, **still open (not merged)**. The rule text therefore names its build ("on a build without VCST-6132 only `password` falls back"), so a run on an older build is not read as a regression.

## Applied (before → after)
- BL-AUTH-016 r1: "Fallback first (on a `password` grant only)" → "Fallback first, on every credential sign-in (`password`, `otp_email`, `mfa`)…".
- BL-AUTH-016 r2: "Refusal only if nothing remains (or the grant is not `password`)" → split per lock and status; on a credential sign-in a lock with nothing accessible left gives 200 with no org.
- BL-AUTH-013: "`invalid_organization_id` … only on a non-`password` grant" → "only on a grant with no fallback".
- BL-AUTH-012 check: "The 400 requires X to be the user's ONLY accessible organization" → "assert the refusal on the explicit switch, never on a credential sign-in".
- IDs, titles, priorities and status are unchanged. No new records and no retirements.

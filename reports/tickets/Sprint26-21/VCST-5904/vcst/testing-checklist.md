## Rules for every lane (read before the first row)

1. **Written offline.** No call to vcst was made to write this file. Every Result and Evidence cell is empty.
2. **Setting re-read, per row.** Shared stand, other testers. Before the first write of a row, the lane re-reads every setting named in that row's `Pre:` through the admin settings REST. The row runs only if each equals its **baseline** or the **last value the ledger records for it**; otherwise the row's Result is `BLOCKED — stand changed by another run: <setting> = <value>` and nothing is written.

   | Setting | Baseline (admin REST, 2026-10-22) |
   |---|---|
   | `MultiFactorAuthentication.Enabled` (global) | false |
   | `MultiFactorAuthentication.StoreMode` (B2B-store) | Use global setting |
   | `OtpSignIn.Enabled` (B2B-store; global false) | true |
   | `TrustedGroups` (B2B-store) | [Electronics] |

3. **Who writes a shared setting.** One lane at a time, by wave order (exploratory, then `ac-checks`, then `ui-checks`). The lane that flips a setting restores it in the same row's Cleanup, reads the value back, and logs flip and restore in `ledger.jsonl` (`entity: setting`). A restore that does not read back = `BLOCKED` for every later row naming that setting, and a STOP to the QA lead.
4. **Global on is the dangerous one.** `MultiFactorAuthentication.Enabled=true` challenges every password sign-in on vcst. Each writing lane opens it for ONE short window covering all of its global-on rows (`ac-checks`: C-1, C-4…; `ui-checks`: its Backoffice rows), closes it in Cleanup, and never signs in as the default admin while it is on (R8). The strategy's single window cannot span a browserless and a browser lane, so there are two windows, one per lane, each ledgered.
5. **Gate.** C-1 runs first in `ac-checks`. If global on does NOT produce `400 two_factor_required` for the created employee, every other row whose Pre names `MultiFactorAuthentication.Enabled` or `StoreMode` is `BLOCKED — enforcement not active (DisableEnforcement suspected); C-1`.
6. **Codes** are read from the notification journal (admin REST), never guessed; a code is per-user single-use, so a row that spends a wrong-code attempt uses its own created user (the attempt counter is per user and shared by the `mfa` grant and the Backoffice).
7. **Oracles.** A row whose Item says *recorded* has a `{HYPOTHESIS}` oracle (two `{SPEC}` that conflict, or no AC): the lane writes what it observed with the request and response excerpt and marks `PASS (recorded)` — never FAIL, never inverted to match the build. Everything else is `{SPEC}`/`{BL}`/`{OBSERVED}` as the Item names it.
8. **Data.** No literal value. Created entities carry the `AGENT-TEST-` prefix, are ledger-logged on creation and deleted in Cleanup. Passwords are read from the env by name, never typed or printed. Accounts and store ids resolve through `process.env` after `config.js`.
9. **Anonymous access probe** (`ac-checks` brief) adds its own `PROBE` rows with the next free `C-n`.

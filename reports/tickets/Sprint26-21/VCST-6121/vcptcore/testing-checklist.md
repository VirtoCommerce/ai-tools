## Rules for every lane (read before the first item)
1. **Oracles.** `{SPEC}` = ticket scope text; `{BL-…}` = oracle; `base:` = the value seen in discovery 2026-10-28 — a BASELINE, never an oracle. Where the spec is silent the item says so and ties it to Q1–Q5; its Result is `PASS (recorded)` with the request/response excerpt, never FAIL and never inverted to match the build. Where `{SPEC}`/`{BL}` and `base:` disagree the item expects the spec and the known defect makes it a FAIL on purpose (items 25, 28, 30, 32) — do not soften it.
2. **Mode.** `RUN` = the verdict rests on it. `RE-CONFIRM` = already observed in discovery; a quick re-check against the same build, marked as such in Evidence. `PENDING-A` = a case for this row is being authored in suites 114/115 (the corpus dispatch links it at 5-report).
3. **Data.** Fixtures are seeded and DISPOSABLE (`TEST_ENV=vcptcore npm run seed:passkey` re-arms: unlock, counter 0, password re-set, leftover keys deleted). One destructive item per account per run; re-arm between items marked ⟲. No literal value: accounts `@td(PK_…)`, store `{{STORE_ID}}` (B2B-store, passkey ON); store-OFF probe store = Clothing. Password is the lane name `DEFAULT_TEST_PASSWORD` (typed by NAME in the browser lane; API calls resolve it through `process.env` after `config.js`). Never sign the browser in as admin; API-side state changes use the env admin token from Node/curl.
4. **Shared stand — settings that move** (read baseline first, flip in the item, restore in the item's Cleanup, read back; a restore that does not read back = `BLOCKED` for every later item naming it + tell the QA lead): B2B-store Passkey scheme `isActive` (24, 25) · Clothing Passkey scheme (24) · B2B-store `MultiFactorAuthentication.StoreMode` (39, 40 — restore within 5 min; every other password sign-in on B2B-store is challenged meanwhile) · `OtpSignIn.Enabled` B2B-store (41) · account locks (2, 26, 27, 28). Created state is made inside the item, never seeded for it (FIFTH RULE).
5. **Lanes.** Chromium only — the WebAuthn virtual authenticator needs CDP: `playwright-chrome` storefront, `playwright-edge` back office. One lane per Playwright server. Authenticator setup is the ONLY CDP use; the ceremony itself is driven by REAL clicks on the page (Add passkey / Sign in with Passkey / autofill) — never `page.evaluate` (the real-user hook blocks it). An assertion needed for an API probe (replay, store-off grant) is CAPTURED from the network of a real click, never minted.

## Setup — virtual authenticator (send ONLY WebAuthn.* commands in this `browser_run_code_unsafe` call; the real-user hook allows exactly that)
```
async (page) => { const c = await page.context().newCDPSession(page); await c.send('WebAuthn.enable'); const r = await c.send('WebAuthn.addVirtualAuthenticator', { options: { protocol: 'ctap2', transport: 'internal', hasResidentKey: true, hasUserVerification: true, isUserVerified: true, automaticPresenceSimulation: true } }); page.__vauth = { c, id: r.authenticatorId }; return r.authenticatorId; }
```
Variants by the same call: `isUserVerified:false` (item 23) · `hasResidentKey:false` (23) · second authenticator for a second key (8) · `WebAuthn.setAutomaticPresenceSimulation {authenticatorId, enabled:false}` · `WebAuthn.getCredentials` / `removeCredential` / `clearCredentials`. **Harness caveats (observed):** Edge create/get silently does nothing without window focus — `browser_tabs select` first, every time. Conditional mediation + presence simulation re-signs the user in SILENTLY on /sign-in load after logout (phantom `Passkey` log rows): when a signed-out state is needed, set presence simulation false before loading /sign-in (turn it on again just before clicking the button) or remove the credential. One click once sent two grants (re-fire suspected) — count grants in the network list before calling it a defect. Never keep a virtual authenticator across items that must not see each other's keys.

The bug and the fix

The module's name pattern rejects names with a digit, _ or @, and that is by design. Before the fix the rejection came back as one bare VALIDATION error with no field or rule, so the storefront could only show "Something went wrong". PR #150 turns each validation failure into its own GraphQL error with extensions.field and extensions.errorCode. A rejected save also no longer leaves the rejected value in the member cache.

Storefront: the error shows on the field

STR 3/3: on /account/profile, Last name "Runner2" is flagged on its input and nothing is saved. Before the fix the page showed only "Something went wrong. Please try again later."

Notes

  • * UnsafeContent was never triggered. javascript:alert(1) in an address line1 was accepted and saved. In a name field, the name pattern rejects it first.
  • Contact.about is not validated: <b>x</b> was saved. This is probably outside the PR's scope.
  • A separate, older defect exists on both builds: reading contact { about } when it is null returns INVALID_OPERATION, and the whole contact comes back null.
  • The header Ship to → Add new dialog shows only the toast, with no error on the field (the error comes back at addresses[1].firstName). This matches the PR's "toast on other pages"; the PR owner should confirm it is intended.
  • Cosmetic: on /account/profile the Last name and Email inputs use the placeholder "Enter your first name".
